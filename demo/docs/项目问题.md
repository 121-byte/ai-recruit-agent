## 问题 1:单岗位候选人匹配在大简历库规模下性能不可接受

**关联代码**:`CandidateMatchService` / `VectorSearchService` / `DocumentChunkMapper.searchResumeByJobChunks`

**现象**
真实模式(DeepSeek + Bailian,`app.mock.enabled=false`)下,6 份简历、单岗位的一次完整匹配(`POST /api/matches/job/{id}/run`)实测耗时 **2.5–3 分钟**,超出同步 HTTP 接口的合理超时——eval 脚本默认 120s 超时被打断,需提到 300s 才跑通(见 `docs/test-data/match.log`)。简历库规模放大到几千份后,耗时进一步恶化。

**根因(两处,性质不同)**

1. **向量召回层未走 ANN 索引,随库规模线性恶化**
   `searchResumeByJobChunks` 用 `JOIN LATERAL (... MIN(rc.embedding <=> jc.embedding) ... GROUP BY rc.parent_id)` 对每个 job chunk 扫描该 `chunk_type` 下**全部** resume chunk。本质是 `O(岗位块数 × 全库简历块数)` 的扫描,且**未走 HNSW ANN 索引**(带聚合的 LATERAL 对 ANN 不友好)。库规模翻倍,该层耗时近似翻倍。

2. **LLM 4 维评估串行,固定成本但单次就很慢**
   Stage-3 对 `DIRECT_EVAL_LIMIT=5` 个候选人**串行**调用 DeepSeek,每次 30–40s,合计 ~3 分钟。与库规模无关,但单次匹配的固定下限就是分钟级。

> 关键认知:**慢的不是"几百份简历",而是召回层没走索引 + LLM 层串行**。单纯加一层过滤解决不了这两个根因。

**延伸担忧(引发本问题记录的直接动因)**

1. 若加一层 boolean 初始过滤筛选出 X 份——**满足条件的可能远高于 X**:硬过滤产出的是无上界集合,若不紧跟 ranked 截断,无上界性会传导到下游昂贵层,只是把瓶颈推到下一层。
2. 若 X 本身就是几百份——**几百份仍全走 chunk 对齐 + LLM 仍不可接受**:即使并发 20 线程,几百 × 30s 也是数十分钟。

两个担忧的共同根因:**任何一层以"集合语义"产出且没有紧跟 ranked 截断,无上界性就会传导到昂贵层把链路打爆。**

**影响**
- 单岗位匹配在几千份简历库下分钟级,无法支撑 HR 实时操作。
- 同步 HTTP 接口超时风险高(已复现 `ReadTimeout`)。
- 库规模继续上升(万级)时,召回层 LATERAL 扫描会从"慢"变"不可用"。
- 即便召回层修快,LLM 串行仍是分钟级,不并发化无法满足交互时效。

**当前基线(供后续优化对比)**
6 份小样本场景实测:MRR=1.0、NDCG@6=1.0、tier_correct_rate=1.0、interview_correct_rate=1.0(见 `docs/test-data/match.log` / `docs/test-data/result.json`)。
