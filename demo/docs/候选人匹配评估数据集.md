# 候选人匹配评估数据集与分级标准

本文档供**多 AI 交叉标注**使用:包含 20 个虚构岗位、60 份虚构简历、grade 分级标准与标注指引。每个 AI 独立对所有(或指定)岗位-简历对打 grade(0-3),最后汇总取共识,作为候选人匹配评估的金标(ground truth),缓解单人标注的主观性。

---

## 一、分级标准(grade 0-3)

### 1. 分级定义

| grade | 含义 | 判定要点 |
|---|---|---|
| **3** | 高度相关 | 核心技能全部命中、项目经历与岗位方向高度吻合、资历(年限/职级/学历)达标或略超 |
| **2** | 相关 | 核心技能大部分命中、项目方向相关、资历达标;存在 1 处可接受的缺口(如缺 1 项次要技能、项目方向略偏) |
| **1** | 边缘 | 方向相关但有明显缺口:缺关键技能、或资历明显不符(过高/过低)、或项目方向偏离需较多适应 |
| **0** | 不相关 | 跨方向、技能基本不重合、资历严重不符(如应届投高级岗)、或简历内容无法支撑岗位 |

### 2. 五维判定(逐维比对,综合定级)

对每对(岗位, 简历),按以下五维逐一比对,再综合:

1. **技能匹配**:岗位"核心技能"与简历"核心技能"的重合度。注意技能变体(如 Spring Boot≈springboot≈Spring Framework;K8s≈Kubernetes;React.js≈React)视为相同。
2. **项目方向匹配**:岗位"项目背景/职责方向"与简历"项目经历"的业务/技术方向吻合度。
3. **资历匹配**:简历"工作年限"与岗位"年限要求"、简历职级与岗位职级是否匹配(过高=overqualified 也降级,过低=underqualified 降级)。
4. **学历匹配**:简历学历/学校/专业与岗位"学历要求"是否达标。
5. **方向一致性**:简历整体职业方向与岗位方向是否同领域(Java 后端 vs Go 后端属相关跨语言,Java 后端 vs 前端属跨方向)。

### 3. 关键判定细则(易混)

- **技能变体视为相同**:"Spring Boot"与"springboot"、"K8s"与"Kubernetes"、"React"与"React.js"、"Vue"与"Vue.js"、"ML"与"机器学习"——不因写法不同降级。
- **overqualified 降级**:8 年资深工程师投"初中级"岗,grade 不升反降(1-2,视资历差距),因存在稳定性风险;但若岗位不拒绝高资历,可维持 2。
- **跨语言同领域**:Java 后端简历投 Go 后端岗,核心后端能力相通但缺 Go 经验 → grade 2(相关)而非 0。
- **跨方向**:Java 后端简历投前端/算法岗 → grade 0(不相关),即便资历达标。
- **部分技能缺口**:岗位要 5 项核心技能,简历命中 4 项缺 1 项次要 → grade 2;缺关键项(如算法岗缺 ML)→ grade 1。
- **资历不符**:应届(0-1 年)投高级岗(5 年要求)→ grade 0;3 年投 5 年要求岗 → grade 1-2(视其他维度)。
- **简历信息不足**:简历项目经历过于简略无法判断方向 → grade 1(边缘,信息不足),不轻易给 0 或 3。

### 4. 不应做的事

- 不因简历"写得好看"加分,只看实质匹配。
- 不因简历"姓名/学校光环"加分(除非岗位明确要求名校)。
- 不给 3.5 等小数,只输出整数 0/1/2/3。
- 不输出"不确定",必须选一个;真模糊时倾向 1(边缘)。

## 四、多 AI 标注指引

### 1. 标注流程

1. 把本文档完整发给每个 AI(DeepSeek / Claude / GPT / Gemini / Qwen 等)。
2. 要求 AI 对**所有岗位-简历对**(20 × 60 = 1200 对)或指定子集(见下)按分级标准独立打 grade。
3. 每个 AI 独立输出,不要让 AI 之间看到彼此结果。
4. 汇总:对每对(岗位, 简历),统计 N 个 AI 的 grade,按规则(下)得出最终金标。

### 2. 输出格式(要求每个 AI 按此输出)

```json
[
  {"jobId": "J1", "resumeId": "R1", "grade": 3, "reason": "技能全命中,项目方向吻合,资历达标"},
  {"jobId": "J1", "resumeId": "R2", "grade": 2, "reason": "..."},
  ...
]
```

`reason` 必填(简短一句),便于分歧时人工复核。

### 3. 配对范围建议

1200 对较多,可分两种粒度:

- **全量(推荐)**:1200 对,统计力最强;AI 能处理,成本可控。
- **抽样**:每岗位选 10 份简历(覆盖 5 方向相关 + 5 不相关)= 200 对,聚焦。

### 4. 汇总规则(得出最终金标)

对每对(岗位, 简历),收集 N 个 AI 的 grade:

1. **完全一致**(N 个 AI 同 grade) → 直接采用,标 `confidence=high`。
2. **多数一致**(≥⌈2N/3⌉ 同 grade) → 采用多数,标 `confidence=mid`。
3. **分歧大**(无 ≥2/3 多数) → 取中位数 grade,标 `confidence=low`;此类样本可标 `difficulty=edge`,评估时单独看或剔除。
4. **一致性度量**:计算 AI 间两两 Cohen's κ(按岗位或全局)。κ≥0.6 说明金标较可靠;κ<0.4 说明分级标准需细化或样本过模糊。

### 5. 汇总后用途

- 把最终金标填回 `src/test/resources/eval/match-cases.json` 格式(`{jobId, relevance:[{resumeId, grade}]}`)。
- **注意 ID 映射**:本文档用 `J1-J20`/`R1-R60` 逻辑编号;入库后 `jobId`/`resumeId` 是数据库主键。需建一份 `J→jobId` / `R→resumeId` 映射表(或入库时简历/岗位 title 直接含 `R1`/`J1` 标识便于反查)。
- 跑 `CandidateMatchEvalTest` 对比模型排序与金标,算 NDCG/MRR/Recall。

### 6. 诚实边界

- **多 AI 一致 ≠ 人类 ground truth**:AI 间一致只说明 grade 对 AI 群体稳定,不等于人类招聘者会同意。但比单人标强。
- **AI 系统性偏差**:若所有 AI 都偏宽松/保守,κ 会虚高。建议至少用 2 家不同厂商的模型(如 DeepSeek + Claude + GPT),降低同源偏差。
- **本数据集为虚构合成**:简历/岗位均为构造,不是真实招聘数据。金标质量受合成设计与 AI 标注共同决定,不宜宣称"匹配准确率",宜表述为"排序自洽性(模型 vs 多 AI 共识金标)"。
