# 意图识别评估边界规范

本文档定义招聘 Agent 意图识别(`IntentRouter`)6 类意图的判定边界、兜底机制、标注规范与难例构造指南。配套评估数据集 `src/test/resources/eval/intent-cases.json`,评估脚本 `IntentEvalTest`。

## 一、六类意图定义

| 意图 | 语义 | 典型措辞 |
|---|---|---|
| **CHITCHAT** | 闲聊/问候/能力咨询/寒暄/感谢/告别,无招聘业务目标 | 你好、你是谁、谢谢、今天天气、辛苦了 |
| **SINGLE_TOOL** | 单一明确的工具操作,有明确对象或可解析参数 | 查张三的面试、搜索五年经验Java简历、看岗位2详情 |
| **COMPOSITE** | 多步骤全流程,显式串联多个**不同类型**操作 | 筛简历→匹配→出题→发offer、全流程招聘、一条龙、从X到Y |
| **HITL** | 高危/不可逆决策,需人工确认 | 发offer、确认录用、淘汰、删除简历、关闭岗位、标记不通过 |
| **BATCH_INDEPENDENT** | 多个**同质独立**任务的批量执行 | 批量发邮件、分别分析3个岗位、给这5人各发邀请、并行处理3份简历 |
| **CLARIFY** | 路由不确定的兜底态(见下节机制) | 帮我看下、那个怎么样、处理一下、查一下 |

## 二、CLARIFY 双兜底机制(原纯代码兜底 → 6 分类 + 置信兜底)

**设计演进(数据驱动)**:初版 CLARIFY 不入 LLM prompt、纯代码兜底(仅 JSON 解析失败时产生)。离线评估 CLARIFY 召回 **0/25 全错**——LLM 把模糊指代脑补成 CHITCHAT/SINGLE_TOOL,代码兜底从不触发。数据推翻旧设计,改为**双兜底**:

1. **LLM 6 分类直出 CLARIFY**:`CLASSIFY_PROMPT` 现含 6 类(含 CLARIFY),LLM 可直接判定"信息不足/指代不明"。
2. **置信度兜底**:LLM 返回任意类别但 `confidence < 0.55` → 回退 CLARIFY(top-2 与全量路径均适用)。

**CLARIFY 期望用例必须是"任何具体分类都不合适"的输入**:缺关键信息(无对象 / 无操作 / 指代不明)。如果输入其实有明确对象+操作(如"查一下张三"虽口语但可判 SINGLE_TOOL),LLM 倾向给 SINGLE_TOOL 而非兜底——这类**不应标 CLARIFY**,应标实际类别。

**标注含义**:expected=CLARIFY 意味着"期望系统也判不准、应反问澄清",不是"输入口语化"。口语化但有明确意图的,标实际意图。

## 三、Pairwise 边界(易混对)

### CLARIFY vs SINGLE_TOOL
- **关键**:有无明确对象 + 可执行操作。
- "查一下" → CLARIFY(无对象);"查张三的面试安排" → SINGLE_TOOL(有对象有操作)。
- "帮我看下" → CLARIFY(无对象);"帮我看下张三的匹配分" → SINGLE_TOOL。
- "那个候选人怎么样" → CLARIFY(指代不明);"张三怎么样" → SINGLE_TOOL(对象明确,可查)。

### CLARIFY vs CHITCHAT
- **关键**:是否隐含业务目标但信息不足。
- "你好" → CHITCHAT(无业务意图);"帮我看下" → CLARIFY(隐含想看业务数据但无对象)。
- "谢谢" → CHITCHAT;"处理一下" → CLARIFY。

### COMPOSITE vs BATCH_INDEPENDENT
- **关键**:串联的是**不同类型**操作还是**同质**操作。
- "筛简历→匹配→出题→发offer" → COMPOSITE(多类型串联);"给5人各发面试邀请" → BATCH(同质操作批量)。
- "解析这3份简历并分别生成面试题" → 看"分别"针对的是同质还是异质;若每份都做相同两步,偏 BATCH;若是筛选→匹配→出题串联,偏 COMPOSITE。**默认:显式多类型串联=COMPOSITE,显式批量同质=BATCH**。

### COMPOSITE vs SINGLE_TOOL
- **关键**:单步还是多步。
- "把这份简历解析一下" → SINGLE_TOOL(单步);"解析简历再匹配再出题" → COMPOSITE(多步)。
- 含"全流程/一条龙/从X到Y/并/然后"显式多步标志 → COMPOSITE。

### HITL vs SINGLE_TOOL
- **关键**:是否不可逆/高危决策。
- "看张三的匹配分" → SINGLE_TOOL(只读);"确认录用张三" → HITL(不可逆)。
- "查面试安排" → SINGLE_TOOL;"把张三标记为不通过" → HITL(改变状态)。
- **HITL 操作词**:发offer、录用、淘汰、删除、关闭、标记结果、确认、拒绝。

### HITL vs BATCH_INDEPENDENT
- "给张三发offer" → HITL(单个高危);"给5人各发offer" → BATCH(批量高危)。**批量高危操作默认 BATCH_INDEPENDENT**(因批量执行模式),但若强调"确认"动作,HITL。**默认:批量= BATCH,单个高危= HITL**。

### HITL vs COMPOSITE
- "发offer给张三" → HITL(单步高危);"筛简历→匹配→发offer" → COMPOSITE(多步含高危)。**含高危步骤的多步流程=COMPOSITE**(HITL 是其最后一环)。

## 四、标注规范

1. **单人标注 + 隔周复标**:每条用例由标注者隔一周复标,两次不一致的剔除或改判,统计 Cohen's κ(一致性)。无第二人时这是最低限度的质量保证。
2. **expected 是"系统应判类别"**:基于本规范判定,不是"输入像哪类"。CLARIFY 尤其注意——只有"系统也应判不准"的才标 CLARIFY。
3. **避免模板套娃**:同义改写要真实多样,不要机械替换人名/技能(如 50 条"查张三/查李四/查王五"算 1 条)。
4. **难例显式标 difficulty**:边界用例、陷阱用例单独标记(数据集可加 `difficulty` 字段,当前评估脚本未读但留扩展)。
5. **不标 LLM 行为**:expected 不基于"LLM 当前会怎么判",而基于"规范上应怎么判"。若 LLM 与规范不符,是 LLM 的问题,数据集不改。

## 五、难例构造四变体

扩充数据集时每类覆盖:

1. **同义改写**:同一意图换措辞(如"搜索五年Java简历"↔"找几个有五年经验的Java后端"↔"五年Java后端的简历有哪些")。
2. **口语化/省略**:去掉主语/量词/动词("查一下"vs"帮我查一下张三的面试")。
3. **多意图/边界**:接近两类的边界(如"这个候选人能录用吗"=HITL 还是 CLARIFY?有对象+高危决策→HITL)。
4. **陷阱**:诱导误判的(如"批量给张三发offer"——"批量"诱导 BATCH,但只1人无批量实质→HITL;"查一下"诱导 CLARIFY 但若"查一下张三"→SINGLE_TOOL)。

## 六、数据集格式

```json
[
  {"input": "查张三的面试安排", "expected": "SINGLE_TOOL"},
  {"input": "那个怎么样", "expected": "CLARIFY"}
]
```

- `input`:用户原始输入(不清洗,保留口语/省略)。
- `expected`:六类之一的大写枚举值。
- 可选扩展字段 `difficulty`(easy/edge/trap)、`note`,当前 `IntentEvalTest` 未读,不影响运行。

## 七、评估方法论:train / held-out 切分(反过拟合)

**铁律:禁止对着 held-out 迭代参数。** 评估数据集每类按前 15 / 后 10 切分:
- **训练集(前 15/类,共 90)**:调参时只看这里的错例,据此改进 prompt / 锚点 / 关键词。
- **留出测试集(后 10/类,共 60)**:`IntentEvalTest` 只在 held-out 上报数,跑一次即定,绝不回头针对它调正则/阈值。

**为什么**:`并` → `并(?!行|且)`、`拒绝.{0,4}` → `拒绝.{0,8}` 这类距离微调是对 eval 曲线拟合(训练集泄漏),对新输入毫无鲁棒性。曾出现 full-150 从 0.64 调到 0.96 的涨幅里相当部分是 eval 拟合而非泛化;回退过拟合部分后,held-out 真实基线为 **0.8333**(Accuracy)、HITL 召回 **1.0000**、CLARIFY 召回 **1.0000**。

**关键词守卫只作 HITL 安全网**:仅覆盖纯状态变更/权限动词(挂起/下线/暂停/删除/归档/撤回/取消/改权限),因 HITL 漏判代价非对称、保守覆盖有独立安全理由。**不设 BATCH/COMPOSITE 关键词守卫**——它们无安全理由,用正则提分即过拟合。BATCH/COMPOSITE/SINGLE_TOOL 的泛化靠 LLM 6 分类语义,成本下降靠真实流量的动态锚点自学习(非静态锚点堆量)。

## 八、当前已知缺口(待数据集扩充后复测)

- CLARIFY 已从 0/25 修复为双兜底(6 分类 + 置信 <0.55),held-out 召回 1.0;扩充用例须严格按第二节标"系统应判不准"的输入。
- COMPOSITE ↔ BATCH_INDEPENDENT 边界混淆:多步顿号列表("分析岗位、筛简历、出题、安排面试")LLM 易判 BATCH(同质独立)而非 COMPOSITE(多类编排),属真实语义边界,需 prompt few-shot 或更细规范界定,不得用正则硬掰。
- held-out 基线 Accuracy 0.83、Macro-F1 0.83:真实泛化水平,后续改进只在训练集上迭代,在 held-out 上一次性复测对比。
- 无指标门禁:当前样本<10 恒 PASS;数据稳定后建议加 Macro-F1 ≥ 阈值的硬门禁。
